1. System Overview

The NewLeaf API is a Fastify + TypeScript service deployed as a Firebase Cloud Function (2nd gen). It serves two main purposes:

  1. Market data feeds — live prices, option chains, indicators, gamma analysis, sentiment
  2. AI-powered trade verification — an 8-agent adversarial pipeline that evaluates trade ideas
Request flow

Client (discover.html / strategy-builder / Invest SPA)
  ↓
POST /verify { ticker, legs, netCredit, modelMode }
  ↓
Auth middleware → validate API key → resolve user tier
  ↓
RBAC middleware → require 'premium' tier
  ↓
VerificationOrchestrator.verify()
  ├─ 4 Analysts (parallel) → evidence
  ├─ 2 Researchers (debate, 2 rounds) → arguments
  ├─ Risk Manager → portfolio fit
  ├─ Judge → verdict + confidence
  └─ Trade Fixer (if marginal/fail) → suggested fix
  ↓
Response { verdict, evidence, debate, riskReport, cost }
  ↓
onSend hook → track LLM usage to Firestore (fire-and-forget)

3. Agent System

Every agent extends BaseAgent<Input, Report> which provides model selection (premium vs budget), structured output parsing via Zod, and cost tracking.

The 8 verification agents

Analyst Technical Analyst

Trend regime (SMA alignment), RSI overbought/oversold, breakout risk vs short strike proximity.

Model: Claude Sonnet / Deepseek
Input: Trade idea + live indicators
Output: Trend state, RSI assessment, risk level

Analyst Gamma Analyst

Gamma wall integrity (0-1), flip distance, band containment. Is spot inside the gamma walls?

Model: Claude Sonnet / Deepseek
Input: Trade idea + OI data + gamma walls
Output: Wall strength, flip risk, containment assessment

Analyst IV Analyst

IV rank, term structure (normal/flat/backwardated), premium fairness (rich/fair/thin).

Model: Claude Haiku / Deepseek
Input: Trade idea + IV surface data
Output: IV assessment, premium quality

Analyst Sentiment Analyst

News polarity (-1 to +1), catalysts in the DTE window, earnings proximity.

Model: Deepseek (always budget)
Input: Trade idea + Serper search results
Output: Polarity score, catalyst list

Researcher Bull Researcher

Advocates FOR the trade using analyst evidence. Round 2: directly rebuts Bear's thesis.

Model: GPT-4 / Deepseek
Rounds: 2 (opening → rebuttal)

Researcher Bear Researcher

Argues AGAINST the trade. Highlights risks the analysts surfaced. Round 2: counters Bull's rebuttal.

Model: GPT-4 / Deepseek
Rounds: 2 (opening → counter-rebuttal)

Risk Risk Manager

Portfolio fit: position count, sector exposure, theta/vega impact. Returns: cleared / reduce_size / blocked.

Model: Claude Sonnet / Deepseek
Input: Evidence + debate + portfolio state

Judge Final Verdict

Weighs all evidence in a fixed hierarchy: Risk > IV > Gamma > Technical > Sentiment. Produces pass/marginal/fail + 0-100 confidence + flip conditions.

Model: Claude Sonnet / Qwen-Max (critical)
Confidence scale:
80-100: strong conviction
60-79: moderate (most evidence aligns)
40-59: low / marginal
0-39: fail territory

Fixer Trade Fixer (conditional)

Only runs if verdict is marginal or fail. Suggests one of three actions:

  • Adjust — same strategy, different strikes (e.g. "move short call from 255 to 260")
  • Wait — condition to re-evaluate (e.g. "wait for IV rank past 35")
  • Switch — different strategy entirely (e.g. "consider a bear put spread instead")

Model: Claude Sonnet / Qwen-Max (critical)

4. Orchestration Flow

The orchestrator (orchestrator.ts, 93 lines) coordinates the 8 agents in a fixed pipeline. It's the single entry point for verification.

Phase 1: EVIDENCE (parallel — 4 concurrent LLM calls)

  ┌─ Technical Analyst ──→ TechnicalReport
  ├─ Gamma Analyst ─────→ GammaReport
  ├─ IV Analyst ────────→ IVReport
  └─ Sentiment Analyst ─→ SentimentReport
                              ↓
                     evidence (aggregate)

Phase 2: DEBATE (sequential — 4 stages)

  Bull R1 ──→ "RSI 58 confirms neutral, theta accelerates..."
  Bear R1 ──→ "IV rank 22 is thin, gamma flip at 1.5 strikes..."
  Bull R2 ──→ "Wall integrity 0.62 has held, premium compensates..."
  Bear R2 ──→ "Wall fails 40% under pressure, credit only 21%..."

Phase 3: RISK

  Risk Manager ──→ { portfolioFit: "reduce_size", thetaImpact, vegaImpact }

Phase 4: VERDICT

  Judge ──→ { call: "marginal", confidence: 51, flipConditions: [...] }

  Weighing hierarchy (hardcoded, non-negotiable):
    1. Risk (hard limits)
    2. IV / premium adequacy
    3. Gamma / flow positioning
    4. Technical / trend
    5. Sentiment (tiebreaker only)

Phase 5: FIX (only if marginal or fail)

  Trade Fixer ──→ { action: "adjust", suggestion: "Move short call to 260" }
Key design decision: Debate over voting. Instead of having analysts vote pass/fail independently (which hides disagreement), the bull/bear debate surfaces the strongest evidence on each side. The judge then weighs it — this produces better verdicts than simple consensus.

6. Market Data Integration

Alpaca (primary)

  • Stock snapshots (OHLCV, bid/ask)
  • Historical bars (250-400 days)
  • Option chains with Greeks (delta, gamma, theta, vega, IV)

Nasdaq (OI data)

  • Real open interest by strike
  • Gamma wall detection
  • Put/call wall identification

Yahoo (fallback)

  • Firebase Cloud Function (Python 3.10)
  • Expiry dates + option chains
  • Used when Alpaca/Nasdaq unavailable

Serper (sentiment)

  • Google News search for ticker
  • Reddit/WSB mentions
  • Social sentiment polarity
Market data is optional. If Alpaca is unavailable (after hours, rate limits), agents reason without live data — they degrade, not fail. The verdict may have lower confidence without live indicators.

7. Authentication & Tiers

Every request (except /health) requires an X-API-Key header. The key resolves to a user tier:

TierLevelAccess
free0Health check, stock snapshots
basic1+ option chains, indicators, gamma, sentiment
premium2+ AI read, recommendations, verification, publishing
admin3+ API key management

Dev mode: DEV_API_KEY env var + DEV_API_ROLE (defaults to admin). No Firestore lookup.

Prod mode: Looks up key in Firestore apiKeys collection. Increments requestCount and updates lastUsedAt on each request (fire-and-forget).

9. LLM Router — Deep Dive

The LLMRouter (llm/router.ts, 252 lines) is the single gateway for ALL LLM calls in the system. No agent calls a model directly — every call goes through the router, which handles provider selection, token counting, cost calculation, and full trace recording.

How tracking works

Every LLM call records two things:

Usage (aggregate)

_usage.push({
  model: 'claude-sonnet',
  inputTokens: 1847,
  outputTokens: 523,
  cost: 0.01339  // USD
});

Returned to the client as response.cost with totals.

Trace (full debug)

_traces.push({
  model: 'claude-sonnet',
  system: "You are a gamma...",
  user: "Analyze AAPL...",
  response: "{wallIntegrity:0.62...",
  inputTokens: 1847,
  outputTokens: 523,
  cost: 0.01339,
  durationMs: 3420
});

Full prompt + response for debugging. Available via response.traces.

Firestore persistence (post-response)

After the response is sent, a Fastify onSend hook writes accumulated usage to the API key's Firestore document — fire-and-forget, never blocks the response:

// app.ts onSend hook — runs after response is sent
apiKeyDocRef.update({
  llmCallCount:  FieldValue.increment(cost.calls.length),   // e.g. +9 for a full verification
  llmTokens:     FieldValue.increment(totalTokens),         // input + output
  llmCost:       FieldValue.increment(totalCost),           // USD, 6 decimal places
  lastTicker:    'AAPL',                                    // from request body
  requestCount:  FieldValue.increment(1),                   // HTTP-level (from auth)
  lastUsedAt:    serverTimestamp()
});

Lifecycle per request

  1. router.resetUsage() — clears _usage[] and _traces[] at the start of each request
  2. Agents call router.call(model, prompt) — each call appends to both arrays
  3. router.getUsage() — returns aggregate (total cost, total tokens, per-call breakdown)
  4. router.getTraces() — returns full prompt/response pairs for debugging
  5. onSend hook — persists totals to Firestore after response

Rate limiting & quotas

Currently: tracking only, no enforcement. The system tracks llmCallCount, llmTokens, and llmCost per API key in Firestore, but does not enforce rate limits or spending caps. This is by design for the current single-tenant setup — the tracking data is available for dashboarding and future enforcement.

To add enforcement, check the accumulated values in the auth middleware before allowing the request: 
// Future: rate limiting in auth middleware
const data = apiKeyDoc.data();
if (data.llmCost > data.costCap) {
  return reply.code(429).send({ error: 'Cost cap exceeded' });
}
if (data.llmCallCount > data.dailyCallLimit) {
  return reply.code(429).send({ error: 'Daily call limit reached' });
}

Mock mode

Setting USE_MOCK_LLM=true returns { mocked: true, model, timestamp } for all calls — zero cost, instant response. Used for integration testing without burning API credits.
