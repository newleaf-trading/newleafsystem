Monorepo Layout Current

Four subfolders, each a logically separate app. NOT npm workspaces — each has its own package.json, dependencies, env files, runtime concerns. They share git history and that's it.

WEB

web/

React app · Picks site + Invest + Workbench

The customer-facing surface. Picks site (public marketing), Invest app (authenticated subscriber), and Workbench (DIY trade builder, served as a static HTML page). All three read from Firestore analyses/{tileId} but none of them write to it.

Owns: user-owned Firestore subcollections only
API

api/

LLM Router + endpoints (TypeScript, Express)

The AI gateway. Every LLM call in the ecosystem routes through api/src/llm/router.ts. Tools, endpoints, orchestrators. Deploys as a Firebase function at cloudfunctions.net/api.

Owns: apiKeys, jobs (Firestore)
PIPELINE

pipeline/

Yahoo OI service + cron schedulers

The always-on data layer. Yahoo OI service serving on localhost:5300. Cron-equivalent jobs via com.newleaf.pipeline LaunchAgent: 15-min fast scan, OI enrichment, daily catchup, health checks. No direct LLM calls — talks to api/ when needed.

Owns: marketState (Firestore), R2 snapshots
GENRECS

generaterecommendations/

Pick generation + tile creation

Candidate scanning, tile creation, weekly workflow. The sole writer to tiles, analyses, weeklyPicks collections after the dual-writer cleanup. Triggered by schedulers in pipeline/.

Owns: tiles, analyses, weeklyPicks, recommendations, pick_outcomes
Why monorepo, not four repos: One backup unit, one push cycle for foundational work, easier cross-subfolder refactoring during the convergence phases. The trade-off is that all four apps share one branch and deploy cycles need to be coordinated. Acceptable for a solo-dev project at this stage.
Operational notes:
  • Per-subfolder dependencies. Each subfolder has its own node_modules (or Python virtualenv) installed independently. No npm workspaces — `npm install` is per-subfolder.
  • Per-subfolder env files. web/.env, api/.env + .env.local + .env.production, generaterecommendations/.env all live locally and are gitignored.
  • Per-subfolder service account keys. Three copies of serviceAccountKey.json in web/scanner/, pipeline/, generaterecommendations/. Same Firebase project, same credentials.
  • Backup-by-default. Pushed to github.com/newleaf-trading/newleafsystem (private). Pre-monorepo, the entire codebase was laptop-disk-only.
  • CLAUDE.md / ARCHITECTURE.md. The monorepo root contains ARCHITECTURE.md as the operational guide for any AI coding tool. Per-subfolder context is in the prose of that file.
What's NOT a monorepo of: shared dependencies, shared build outputs, shared TypeScript configs, npm workspaces, lerna, Nx, Turborepo. We deliberately kept each subfolder independent. If we later want shared tooling, we add it; we did not pre-emptively over-architect.
The Three Products As-Is

NewLeaf has three customer-facing surfaces, intentionally distinct. The system isn't "duplicated" — it's three products sharing inconsistently-implemented primitives below the product layer. The architecture work is at that primitive layer, not at the product layer.

INVEST

NewLeaf Invest

newleafsystem.com/invest/strategy/{id}

Authenticated investor app. Five-phase lifecycle: Discover → Decide → Build → Execute → Defend. Curated picks consumed inside a workflow with sizing, broker handoff, and position management. Reads from Firestore analyses/{tileId}.

Audience: Paying subscribers
PICKS

NewLeaf Picks

newleafsystem.com/picks/analysis/{ticker}

Public marketing/acquisition site. Same tile content rendered for non-subscribers, with a downloadable 12-page PDF report. Same Firestore source as Invest. PDF generated separately by WeasyPrint from a local enriched JSON file.

Audience: Acquisition
WORKBENCH

NewLeaf Workbench

newleafsystem.com/workbench/discover.html

DIY trade builder. User picks ticker, builds their own trade with sliders, runs the 8-agent /verify orchestrator. Outputs ephemeral recommendations and verifications. Today: does not publish to picks/invest.

Audience: DIY traders
Key insight: Two products (Invest, Picks) consume the same Firestore analyses/{tileId} documents. They are not separate publishing pipelines. They are two render surfaces over one data source. Whoever writes to analyses/{tileId} is the publisher. Today that's the manually-run pipeline/publish-pick.cjs. The convergence question is: should the workbench be allowed to write there too?

Read the matrix as effort scoping. 9 fields are direct passthrough. 4 fields are preserved from verify output (bull/bear/debate/verdict) — these reclassify from "synthesise" to "render as-is," which is the single biggest change from v1. 6 partial fields need transformation or a synthesis call (~1-2 days). 5 missing fields need new tools or new synthesis logic (~2-3 days). The synthesis adapter now does narrative-only work — strategy rationale, key levels with reasoning, exit strategy detail, support/resistance descriptions, sentiment driver attribution. The verify output's adversarial reasoning becomes product content, not raw material.
Publish gate: deterministic, no override. The publish-pick endpoint accepts a verify_job_id and gates on two conditions: verdict.call === 'pass' AND verdict.confidence >= 65. Marginal verdicts and low-confidence passes go to a review queue. No analyst override path — discipline over flexibility. The verify_verdict and verify_confidence values are stored in the published doc as provenance (constant in v1, but kept for forward-compatibility).
Problems Found Issues

Eight problems were identified across v2/v3 audits. Two are resolved by this session's migration work. Six remain — most are part of the forward plan (F1-F5).

P0 Dual-writer drift on production Firestore
Three production collections (tiles, analyses, weeklyPicks) had writers in both newleafsystem and newleaf-generaterecommendations. Resolved by Batch B: legacy newleafsystem copies deleted; generaterecommendations/ is now sole writer for these collections.
P1 workbench/discover.html not in git
Workbench production page was untracked. Resolved by monorepo migration — now committed under web/workbench/ as part of the initial commit. Audit confirmed the embedded values (NewLeaf API key, Firebase web config) are public-by-design client keys, safe to commit.
P2 scanner/config.json contains live secrets
API keys for Alpaca, R2, SMTP, Grok, and Gemini were hard-coded in scanner/config.json, present in two repos. Resolved structurally: the file is now gitignored in the monorepo (no longer ends up in any commit). Rotation deferred per the D-keys decision; monitoring instead.
P3 MACD values are LLM-hallucinated
The published analysis JSON contains MACD line, signal line, and histogram values (e.g. macdLine: 0.85, signalLine: 1.12, histogram: -0.27) but MACD is not calculated anywhere in the codebase. These numbers are generated by Claude based on RSI/BB/SMA context. Eventually a user will compare against a charting tool and find the discrepancy.
P4 Two sentiment implementations with different math
Pipeline runs 4 engines (Claude + Grok + Gemini + Reddit) at weights 30/25/25/20. API runs 3 engines (no Claude) at weights 35/35/30. Same ticker, same day, different score. When pipeline's Claude engine errors, weights renormalise to 33/33/27 — still different from API's 35/35/30. Both engines were added in their respective initial commits; this isn't drift, it's parallel build.
P5 Data source divergence: pipeline vs API
OI: Pipeline uses Yahoo (local Python :5300), API uses Nasdaq. Gamma walls: Pipeline uses 3-factor scoring (OI + delta + volume), API uses simple OI concentration. Earnings: Pipeline has static JSON file, API has nothing. News: Pipeline uses Claude WebSearch, API uses Serper. Different stacks produce different underlying numbers, not just different prose.
P6 Pipeline AI calls have zero observability
5 AI invocation paths bypass the LLM router: Claude CLI in analyse-tiles, Claude CLI in sentiment-engine, Grok REST in sentiment-engine, Gemini SDK in sentiment-engine, and Firebase aiChat's Gemini SDK call. None are cost-tracked. None are version-pinned. None have token counts. The Claude CLI calls have a 5-minute timeout and can fail silently.
P7 Publishing is manual and undocumented
publish-pick.cjs is run by hand. create-weekly-picks.js exists but is not in cron — only npm run picks:preview for dry-run is referenced. Picks per week is 5–10, manually selected. This is actually compatible with a workbench-as-authoring-tool flow — the human-in-the-loop model is already in place; the tool just changes.
P8 No provenance on pick_outcomes
The pick_outcomes Firestore collection (used to track win rate) does not record which model produced the pick, which prompt version, or which analysis source. Win-rate changes cannot be attributed to model or prompt changes. This makes future A/B comparison impossible and must be fixed before any new analysis path writes picks.

Decisions Log Living document

A running log of decisions made across the v1-v4 deck progression. Resolved decisions are kept here for context (so future you knows why the system is the way it is). Open decisions are at the bottom.

D-publish · Publish gate logic RESOLVED

Locked: Only verdict.call === 'pass' picks publish. Marginal verdicts go to a review queue (no analyst override). Discipline over flexibility — if marginal becomes a regular occurrence, the orchestrator rubric needs tuning, not a bypass.
  1. Pass-only, no override (chosen) — deterministic publish gate. Hard discipline.
  2. Pass + optional analyst override for marginal — rejected. Creates a discipline-erosion habit and a provenance question.
  3. Marginal publishes with a "tentative" label — rejected. Mixes brand promise across published picks.

D-product · Picks vs Invest content split RESOLVED

Locked: Picks carries the full adversarial analysis (bull case, bear case, debate, key levels, sentiment with attribution, flip conditions). D1 · Synthesis adapter design

  1. Single Sonnet call, narrative-only (recommended) — verify output (verdict, debate, bull/bear, risk, suggested fix) is preserved as-is. Sonnet synthesises only the narrative gaps: strategy rationale prose, key levels with reasoning, exit strategy detail, alternatives considered, sentiment driver attribution. ~$0.20/pick, 20-30s.
  2. Composed: preserve verify + Haiku for narrative gaps — cheaper (~$0.04) but inconsistent prose voice between preserved sections and Haiku-generated ones.
  3. No synthesis, ship with gaps — only render what verify produces. Misses strategy rationale, key levels, alternatives entirely. Page reads thinner than current pipeline output.

D2 · OI data source consolidation

  1. Keep Yahoo via local Python service (recommended) — it's the only real OI source today; pipeline already proves it works. Port the wrapper to API tools.
  2. Move to Nasdaq API only — already in API but unproven for pipeline-grade gamma. Risk: gamma walls change shape.

  1. premium (recommended) — Sonnet across the board, ~$0.50/pick verify + ~$0.20 synthesis = ~$0.70/pick. ~$7/week at 10 picks/week. For paying-product output, quality matters more than savings.
  2. budget-qwq — current default in discover.html, ~$0.05/pick. Risk: published pick quality drops below current pipeline baseline.

D4 · What happens to picks published under the old flow

  1. Freeze (recommended) — leave existing picks alone, only new picks use new flow. Simplest. Win-rate comparison limited until enough new picks accumulate.
  2. Backfill provenance only — add analysis_source: 'pipeline-v1' to existing docs, no content change. Slightly better for analytics.
  3. Republish through new flow — re-run synthesis on existing picks. Highest effort, would change content, not recommended.

D7 · Minimum conviction floor for publish (new)

  1. 65/100 (recommended) — a pass verdict at 52% reads as uncertain to a paying reader. Setting a floor above the verify-pass threshold ensures published picks signal genuine conviction.
  2. 60/100 — slightly looser; preserves more candidates as publishable. Risk: borderline picks get through.
  3. No floor — anything verify calls 'pass' publishes. Simplest, but couples publish quality to whatever verify defines as the pass threshold.
