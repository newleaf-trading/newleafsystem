SEPA Trend Filter

A deterministic Minervini-style trend overlay that judges reversion-engine candidates — what we built, and how it differs from the reversion-only scanner.

Status: Forward-test accruing Branch: sepa-trend-filter Deployed: no (local only) Date: 2026-06-20
TL;DR

The Movement & Range scanner is a reversion engine — it scores support/resistance zones by how reliably they've held and suggests selling premium against them. Its blind spot: it has no opinion on the trend carrying price into the zone, so it ranks a support sitting in a multi-year downtrend (TLT, NVO) as a top bull-put-spread candidate — a falling knife. We added a deterministic SEPA trend template that judges existing candidates (it does not generate new ones): each gets a verdict — aligned (endorse), neutral (unchanged), or conflicted (demote the knife). It's pure, LLM-free in its decision, and its penalty multipliers are unvalidated placeholders being tuned by a forward-test, not yet wired into any live surface.

1. The problem: a reversion engine blind to trend

The existing engine (shared/reaction/ v2, surfaced in workbench/movement-range.html) is deterministic and good at what it does:

  • Clusters support/resistance levels (gamma walls, moving averages, swings) into zones.
  • Scores each zone by touch-count and Wilson-smoothed hold-rate — "how reliably has this level held?"
  • Produces a composite setupQuality (0–100) and suggests a premium-selling structure (bull-put-spread at support, etc.).
The blind spot

It judges the zone, never the trend carrying price into the zone. A support with a great historical hold-rate that now sits in a sustained downtrend gets ranked as a top "Tradeable" bull-put candidate — exactly the falling-knife trade a premium seller must avoid. There was already an approach-velocity guard (caps score when price reaches a zone faster than 3×ATR), but that catches a fast arrival, not a slow multi-month trend.

2. What we built: the trend overlay

A pure, deterministic SEPA-style trend template (Minervini) in shared/trend/trend-template.cjs. It is an overlay: computeTrendTemplate({ bars, benchmarkBars, … }) consumes a candidate's price history plus a benchmark and emits a verdict. It generates nothing.

Six gating checks (all from price; SMAs reused from shared/indicators, never re-implemented)

CheckMeaning
maStackSMA50 > SMA150 > SMA200 (orderly stack)
priceAboveStackclose > SMA50 and > SMA200
ma200RisingSMA200 today > SMA200 ~20 bars ago
rsPositiverelative strength vs benchmark positive and rising
near52wHigh / off52wLowwithin 25% of the 1y high / ≥25% above the 1y low
vcpActivevolatility-contraction base: pullbacks tightening + volume drying

The verdict

aligned — endorse

All four up-core checks hold (stack, price above, SMA200 rising, RS positive).

SQ + alignBonus (+5)

neutral — unchanged

No trend opinion. If a VCP base is tightening, premium is discounted (imminent expansion).

SQ × vcpNeutralMult (0.85)
else unchanged

conflicted — demote

Any 3 of 4 down-core (inverted stack, below SMA200, RS negative, SMA200 falling) — the falling knife.

SQ × conflictMult (0.6)

The verdict scales the engine's existing setupQuality via adjustedSetupQuality(originalSQ) — it never invents a score, it only re-weights the one the reversion engine already produced.

It keeps the patterns that worked — deterministic decides, LLM narrates, and inject the verdict as authoritative ground truth (the MACD-fix pattern) — and explicitly guards against the regime double-counting class from Discover Pro: when both the new trend penalty and the existing approach-velocity guard fire on the same knife, the module emits an overlap flag so the redundancy can be measured rather than silently charging the same risk twice.

5. Key design decisions

Asymmetric verdict

Endorsement is expensive (all four up-core checks), demotion is eager (3 of 4 down-core). The 3-of-4 lets conflicted fire before SMA200 rolls over (the lagging member), so falling knives are flagged early rather than late.

Multiplicative penalty, not flat

A flat penalty under-punishes the highest-scoring knives — the most dangerous ones. A multiplier scales with the candidate's own score. conflictMultiplier and vcpNeutralMultiplier are placeholders (0.6 / 0.85) until the forward-test sets them; alignBonus stays additive so endorsement can't inflate a score.

VCP suppresses neutral premium only

A tightening base under a neutral verdict signals imminent expansion — the worst entry for a premium seller — so it discounts the score. Under aligned, an upside breakout helps a bull-put, so VCP is deliberately not penalized there.

Overlap instrumentation (measure, don't guess)

The module never imports score.cjs; the caller passes velocityGuardFired, and the module emits overlap = conflicted && velocityGuardFired. Whether to suppress one penalty when both fire is a Phase-3 decision driven by data — Phase 2 only measures.

6. Validation: why forward-test, not backtest

The retrospective backtest is impossible

The reaction engine's setupQuality is computed live (scanner UI / tests) but never persisted to any dated store. Reconstructing it from EOD can't reproduce the zone/IV/OI inputs and would breach the consistency bar. So there is no historical candidate stream to backtest against — the study must run forward.

The forward-test therefore:

  • Accrues a faithful candidate snapshot every Friday (version-stamped, so weeks where scoring drifts can be segmented out).
  • Labels each candidate only after its 21-trading-day window matures — outcomes are null until then.
  • No lookahead: template inputs strictly pre-signal, outcome inputs strictly post-signal — enforced by a mandatory leakage test (green now, before any real data) that includes an adversarial control proving the window filter is load-bearing.
  • Train/holdout, not fit-to-noise: the multiplier sweep (deferred until n≥100) sets values on an earlier half and validates on a later half; a multiplier that only works in-sample is noise.
  • Can return null: if conflicted doesn't breach more than aligned within a fixed setupQuality band, the filter is redundant there and we say so — no tuning until signal appears.

8. Current status & what's deployed

Nothing is deployed to Firebase

All of it is local on the sepa-trend-filter branch. Phase 2+3 are committed locally (a7633b9); Phase 3b is uncommitted pending review. The accrual job runs on the local launchd pipeline daemon (not Firebase) and writes a local, gitignored candidate store. Nothing touches Firestore, Cloud Functions, Hosting, or any UI — by design, the placeholders are unvalidated.

First snapshot (2026-W25), for scale

  • 296 symbols scored · verdicts: aligned 63 · neutral 142 · conflicted 91
  • Primary cohort (bull-put-at-support): 18, of which 6 conflicted — far below the ~100 needed; power is the binding constraint, ~months of accrual required.
  • Overlap (conflicted + velocity guard): 15 — co-occurrence is being tracked, not yet analyzed.
