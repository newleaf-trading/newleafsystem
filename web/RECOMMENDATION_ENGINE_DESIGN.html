At a glance

One pass, five stages, zero model calls to decide

Each stage is a pure function with fixed thresholds. The same market inputs always produce the same trade — auditable, testable, and free to run. An LLM is invoked once at the end, only to write the English explanation.

01Why deterministic

The system used to ask an LLM to choose the strategy, the decision, the confidence, and the risk plan. The evidence said that step earned nothing.

  • 12 models, one answer. Fanned across qwen/claude/gemini/gpt/grok/deepseek, every model just echoed the engine's candidate. When 12 stochastic systems agree, the input determined the output — the LLM was a paid identity function.
  • The rules were already deterministic. The prompt had become a decision tree of numeric thresholds (ADX ≥ 25, RSI < 30, …). Running a decision tree through a transformer pays for nondeterminism on logic code does perfectly.
  • LLM confidence was theater. Self-reported 0–100, clustered 60–85, incomparable across models, and impossible to calibrate. The engine's score is deterministic, so it can be calibrated against real outcomes.
  • The LLM missed the one real bug. Several models approved a structurally invalid butterfly. The correctness risk lived in deterministic leg code, not in strategy choice.

Conclusion: selection, regime, decision, confidence and risk plan move to code. The LLM keeps exactly one job it does better than code — writing the explanation.

The guiding principle: use the LLM at build time to write deterministic code (these modules were authored + property-tested by a frontier model), not at run time to make decisions. The model's judgment is frozen into tested code that then runs identically forever.

04Regime — classify by numeric rules

decision-engine.ts → classifyRegime(). Pure thresholds, evaluated top to bottom. First match wins.

aboveBoth = spot > SMA20 AND spot > SMA50
belowBoth = spot < SMA20 AND spot < SMA50

if ADX ≥ 25 and aboveBoth  → Bullish trend continuation
if ADX ≥ 25 and belowBoth  → Bearish trend continuation
   └ tiebreak: a counter RSI extreme overrides to mean-reversion
     ONLY when ADX < 35 (a strong trend dominates RSI)

else if RSI < 30 and ADX < 25 → Oversold mean-reversion
else if RSI > 70 and ADX < 25 → Overbought mean-reversion

else if ADX 20–25 and aboveBoth → Developing bullish trend   ← closed gap
else if ADX 20–25 and belowBoth → Developing bearish trend

else if ADX < 20 and reliableBand and spotInsideBand
                              → Range-bound premium selling

else                          → No-trade / wait

The Developing trend bucket (ADX 20–25 with a clean MA stack) was added to close a coverage gap that used to force otherwise-tradeable directional setups into No-trade.

05Decision — tiers & guardrails

decision-engine.ts → buildDecision(). The engine's 0–100 score sets the tier; guardrails can only downgrade, never promote.

// hard fails — checked first
no valid legs               → NO_TRADE
≥2 inputs missing & no thesis → DATA_ERROR
regime = No-trade / wait     → NO_TRADE

// score tiers
score ≥ 65 → APPROVED_TRADE
score 40–64 → WATCHLIST_TRADE
score < 40 → NO_TRADE

// guardrails — downgrade APPROVED → WATCHLIST only
all gates failed (passedGates == 0)   → cap + flag no_gates_passed
premium-selling with no IV / vol data → cap + flag missing_vol_data
regime = Developing trend             → cap + flag moderate_adx

confidence = engine score      direction = engine's reconciled direction
risk plan  = per-strategy template (50% credit target · 2× stop · band-breach kill)

Decision meanings

approved strong setup, risk acceptable (score ≥ 65, no caps).

watchlist valid but elevated risk (40–64, or capped from approved).

no trade no valid candidate, or no constructible legs.

Why guardrails only downgrade

Each guardrail encodes a known risk the raw score doesn't fully price (thin conviction, missing vol, moderate trend). They tighten the bar — they never loosen it. A trade can lose its approval to a flag, but a flag can never manufacture one.

06Leg construction — valid or nothing

leg-builder.ts. The real money-losing surface. The contract is now: a builder returns structurally-valid legs or none at all — never a structure that contradicts its label.

  • Direction is a hard constraint. snapToChain snaps to real strikes, but a "down" wing can never be pulled up to a nearer liquid strike (the bug that silently turned a broken-wing butterfly into a symmetric one).
  • Broken wing guaranteed asymmetric. pickBrokenWing places the broken wing strictly wider than the near wing, or returns null.
  • Self-validating & fail-closed. buildLegs runs validateStrategy on its own output; invalid topology ⇒ no legs ⇒ the decision becomes no trade.
Why fail-closed beats best-effort: a mislabelled structure has a different risk profile than its label promises (a symmetric debit fly vs a credit broken-wing with no risk on one side). Showing a user “no valid structure at acceptable liquidity” is strictly safer than shipping the wrong trade under the right name.

07Worked examples

Same engine, same thresholds — the regime rule is what splits the outcome.

ABNB · spot 131.97 · ADX 7.1 · RSI 50 · IV/RV 1.49 · inside band 115–133 · score 97
regime   ADX 7.1 < 20, reliable band, spot inside  → Range-bound premium selling
decision score 97 ≥ 65 → APPROVED. No guardrail fires.
legs     BUY put 125 / SELL 2× put 119 / BUY put 105   (wings 6 vs 14 → asymmetric ✓)
result   APPROVED_TRADE · broken_wing_butterfly
META · spot 566 · ADX 23.4 · below both SMAs · score 98 · 2 gates passed
regime   ADX 23.4 ∈ 20–25 + belowBoth → Developing bearish trend
decision score 98 ≥ 65 → APPROVED… but Developing-trend guardrail caps it
result   WATCHLIST_TRADE  (flag: moderate_adx)

Near-identical scores (97 vs 98), different decisions — purely because a regime rule fired a cap. Every branch is inspectable and changeable in one line.

08The LLM's role — narration only

The decision is finished before any model is called. The LLM only renders the engine's facts into prose, and it can fail without breaking the product.

  • Inputs are facts, not questions. Decision, regime, strategy, score, walls, risk plan — the model rewrites them into ≤80 words and may not introduce a number, strike, strategy, or direction not present.
  • Template fallback. If the narration call fails, a deterministic template rationale is used. The recommendation is always complete and correct.
  • Internal consistency for free. Because the narration is generated from the panels, it cannot contradict them.
  • The multi-model page is now an eval tool. Since selection is deterministic, all models agree on the decision and differ only in prose — useful for comparing narration quality and the adapter layer, not for picking trades.

09Outcome tracking — the payoff of going deterministic

Every production recommendation is persisted to Firestore recommendation_snapshots (awaited, so Cloud Run can't drop the write).

Each snapshot captures: ticker · expiry · spot · decision · strategy · direction · regime · score · pillars · gateValues · legs · dataFlags · riskPlan · timestamp.

A deterministic score is the only confidence that can be calibrated: the same inputs always produce the same score, so it can be correlated to realized P&L. An LLM's per-call vibe cannot. This snapshot stream is what lets the engine's weights eventually be tuned against outcomes instead of intuition.
